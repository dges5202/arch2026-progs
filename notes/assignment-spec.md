## Project Overview

This project challenges you to develop a simple system using RISC-V assembly language. Throughout the process, you will explore essential low-level programming concepts, such as:

- Efficient use of registers for optimized code execution.
- Writing functions and adhering to RISC-V calling conventions for both internal and external functions.
- Memory management with static data and the stack; the bare-metal playground has no allocator, so supply your own (e.g., a bump allocator) if a program needs one.

1. `make` builds the toolchain check, the rv32emu emulator and the default `-O2` ELFs, and installs the Git hooks. Each program becomes a bare-metal ELF that links `src//` (C and assembly objects separately) with the fixed runtime in `common/`; its `main` runs the tests and returns 0 only if all pass.
2. Write the C version first. Replace the dummy in `src//.c` so that it follows the contract header exactly, then run `make test` (all four levels) and `make sanitize` (host build under AddressSanitizer and UndefinedBehaviorSanitizer). The test output names the failing case.
3. Write the assembly version in `src//.S` with the `_asm` symbols of the table. The tests cross-check it against the C version on every input they use, so the two must return the same results, including the error returns.
4. Make it fast and small. The driver counts the instructions each function retires and fails a function that exceeds its budget in the header or that is slower than the best C build. `make dump` writes the listings, `make size` the section sizes and `make cycles` the cycle tables; use them for the comparison that items 4 and 5 ask for.
5. Commit in small steps from a terminal. The hooks check formatting, unsafe functions, static analysis, the commit message and the `Change-Id` chain; a commit that fails a check is rejected.
6. Push to `main`. GitHub Actions runs `lint`, `chain` and `grade` (see item 11): the last repeats the checks with the instructor's harness and grades only your `src//` files.

## RV32I Feasibility and Optimization Leads

All four programs can run under the RV32I-only rule. The notes below record what each needs and where to look for gains; they are starting points, not the answer. The contract header of each program is authoritative; the quiz code is the C baseline where a header does not say otherwise, and you measure every optimization against it.

Compiling the C fragments of the three quizzes with GCC 15.2.0 (`-march=rv32i_zicsr -mabi=ilp32 -ffreestanding`, at `-O2` and at `-Os`) leaves only `__mulsi3` and `__muldi3` unresolved. No division helper is needed: `/ 128` becomes a shift. The runtime supplies `__mulsi3`, not `__muldi3`, and the link (`nm -u`) fails on any other missing symbol.
